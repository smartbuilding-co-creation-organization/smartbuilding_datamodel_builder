# Issue 対応ワークフロー

GitHub Issue を受け取ってから main へマージし、ブランチを削除するまでの手順を定義する。
AGENTS.md の「5. 作業フロー」を Issue 起点の運用として具体化したもので、優先関係は
AGENTS.md > 本書 > 個別 PR の判断とする。

## 全体の流れ

```text
Issue 確認 → トリアージ → plans.md へバックログ化 → TDD 実装 → PR 発行
   → CI green → codex review → 指摘対応 → マージ → ブランチ削除 → Issue close
```

## 1. Issue 確認

- Open Issue を一覧し、以下を確認する。
  - 報告された事象がコード上のどこに対応するか（ファイル・行）
  - 報告時点のコミットと現在の `main` の差分（既に修正済みでないか）
  - 既存の plans.md タスク・マイルストーンとの対応関係
- 「コードを読んで確認した事実」と「Issue 本文の主張」を分けて記録する。本文の主張が
  現行実装と食い違う場合は、根拠となるファイル・行を挙げて差分を示す。

## 2. トリアージ判定

各 Issue を次の 4 分類のいずれかに割り当てる。

| 判定 | 意味 | 次のアクション |
| --- | --- | --- |
| 要対応 | 現行実装に未対応の不具合・欠落がある | plans.md にタスク化して実装する |
| 要合意 | 実装方針が他リポジトリ・他チームとの取り決めに依存する | plans.md に論点を記載し、合意を待つ |
| 対応済 | 受入基準を現行実装が満たしている | 根拠を記録し、報告者の確認を経て close する |
| 対象外 | スコープ外、または非目標として合意済み | 理由を Issue へ記載して close する |

- 「対応済」と判定する場合は、受入基準の 1 項目ごとに根拠（ファイル・行・CI の実行結果）を
  示す。根拠を示せない項目が 1 つでも残る場合は「対応済」にしない。
- 報告者以外が close 可否を判断しない。判定と根拠を提示し、close は報告者または
  メンテナが行う。

## 3. plans.md へのバックログ化

- AGENTS.md の「plans.md に記載のない作業を行う場合は、先に plans.md を更新する」に従い、
  実装着手より前に plans.md へ登録する。
- 「要対応」「要合意」は `## 2.x` の節として追加し、次の見出しを必ず含める。
  - 目的 / 現状確認 / 設計方針 / 対象パス / 受入基準 / 非目標
- 「対応済」「対象外」は該当マイルストーンの棚卸し表に判定と根拠を追記する。
- 受入基準は unit または E2E で検証できる粒度で書く（AGENTS.md「4. テスト規約」）。

## 4. TDD 実装

1. **Red**: 受入基準を満たさないことを示すテストを先に書き、失敗することを確認する。
   - core のロジックは `packages/core/test/`、CLI は `apps/cli/test/`、UI 操作は
     `apps/web/e2e/` に置く。
   - 仕様変更の場合は、既存テストの期待値を先に更新する（AGENTS.md「4. テスト規約」）。
2. **Green**: テストが通る最小の実装を入れる。
3. **Refactor**: 重複と命名を整理し、テストが通ったままであることを確認する。
4. 変更範囲に応じて AGENTS.md「3. 品質ゲート」の最低実行マトリクスを満たす。

## 5. PR 発行

- 1 PR = 1 意図。バックログ化（文書）と実装（コード）は分ける。
- ブランチ名は `feat/<topic>` / `fix/<topic>` / `chore/<topic>` / `docs/<topic>`。
  エージェントが作業する場合は指定されたブランチを使う。
- `.github/PULL_REQUEST_TEMPLATE.md` の全項目を埋める。Verification のチェックは
  実際に実行したものだけを付け、省略した場合は理由を書く。
- PR 本文に対応 Issue 番号（`Refs #40` など）と plans.md の節番号を明記する。
  Issue の close は報告者の確認後に行うため、`Fixes #40` は原則使わない。

## 6. CI と codex review

- CI（`.github/workflows/ci.yml`）が green になるまでマージしない。
  失敗は再実行で流さず、原因を特定して修正する。
- codex review の指摘は次のいずれかで必ず決着させる。
  - 指摘どおり修正して push する
  - 修正しない場合、その理由を当該スレッドに返信する
- 指摘対応の push ごとに CI を green に戻す。レビュー往復に上限は設けない。

## 7. マージとブランチ削除

- マージ条件は「CI green」「codex review の指摘が全て決着」「PR テンプレートの
  Verification が埋まっている」の 3 つを全て満たすこと。
- マージ方法はリポジトリの既定（squash）に従い、コミットメッセージは
  Conventional Commits（AGENTS.md「6. コミット規約」）にする。
- マージ後に作業ブランチを削除する。

```bash
git push origin --delete <branch-name>
```

## 8. Issue close と plans.md 更新

- マージ後、plans.md の該当タスクを Done / Completed に更新する（同じ PR に含めてよい）。
- Issue には「どの PR でどう直したか」「残る制約は何か」を記載し、報告者の確認を経て
  close する。
- トラッキング Issue がある場合は、子 Issue の判定が揃ってから close する。
